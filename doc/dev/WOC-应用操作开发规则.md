# WOC 应用操作开发规则

本文件是新增、修改应用操作时的必读规范，汇总用户确认的职责边界。适用于 daemon、WOC HTTP/MCP、客户端 Skill 及工作流脚本；当前实现微信，后续应用沿用相同原则。组件拓扑和现有实现见 [系统架构](WOC-Cua-系统架构.md)，仓库开发入口见 [AGENTS.md](../../AGENTS.md)。

## 1. 操作放在哪一层

| 能力类型 | 归属 | 判断标准 |
| --- | --- | --- |
| 数据库查询、本地附件读取/解密/导出 | wx-cli；daemon 提供受限适配 | 处理已经存在的本地数据，不操作 UI，不联网补下载 |
| 应用专属的观察、短操作 | woc-daemon 的应用适配器 | 前置条件清楚、执行短且有界、结果可核对，例如观察页面、切到指定导航页、填入当前聊天草稿、发送已核对的草稿 |
| 认证、机器 ACL、写锁检查、路由、在途保护 | WOC HTTP 网关 | 决定请求是否允许执行、转发到哪台机器；不负责业务流程编排 |
| 向 Agent 暴露能力、传递参数与结构化结果 | WOC MCP 适配层 | 复用 HTTP 契约，保留错误详情；不再复制一套业务流程或锁状态 |
| 常用且步骤、分支明确的多步流程 | 客户端 Skill 附带脚本 | 直接调用多个认证 HTTP/MCP 操作，按结果 if/else；正常路径不用模型逐步指挥 |
| 需要看界面、消歧、选择或异常决策的步骤 | SKILL.md 指导 Agent | 写明何时运行哪个脚本、所需参数和授权、何时停止并交给 Agent 观察 |
| 通用截图、点击、键盘、滚动、窗口操作 | 原生 Cua | 保留通用 computer-use；不在 WOC 再造一套任意坐标/按键/脚本接口 |

**daemon 的“原子”是业务边界，不要求只有一次鼠标点击，也不承诺事务回滚。** 例如在已识别的微信浏览器里展开输入框、填 URL、核对、回车，可以构成一个短操作。它不应顺带启动缺失的浏览器、寻找历史消息、反复滚动或等待文件下载。

只有特别高频、稳定、前置条件明确且仍然短而有界的小流程，才考虑合并进 daemon；在变更说明中交代合并理由、执行上限和失败语义。长流程保留在客户端；将来确需服务端长任务时单独设计进度与取消，不能把它伪装成原子接口。

## 2. 调用方向与权限

```text
Agent / Skill 脚本 → WOC MCP 或认证 HTTP → WOC 网关 → daemon → 本地执行
                 ← 结果 / 错误 / 缺失前置条件 ←

Agent / Skill → 原生 Cua MCP → 受管 Cua 网关 → cua-spacesd
```

- 客户端 Agent/脚本显式申请、释放同一台机器的写锁；网关是锁状态的权威。daemon 不回调网关，不获取/释放锁；网关和 MCP 不代替客户端自动获锁或补做 GUI 前置步骤。
- 锁按实际副作用分类。截图、结构观察、查询已有数据不需要 GUI 写锁，也不续期；点击、滚动、输入、切换或打开应用/页面需要锁。不要因为操作名叫“读取”就隐式切聊天或触发下载；这些 GUI 步骤必须拆成写操作。
- Skill 脚本直接调用 HTTP 仍须经过同一网关、凭证、ACL 和写锁检查，不直连内部 daemon。写操作使用已取得的控制周期；结束、失败或等待外部决策时释放。失锁后停止写入并重新观察，不循环抢锁，不用 shell 或其他入口绕过拒绝。
- 同一客户端凭证的工作流按机器串行。人工交接沿用现有在途操作保护，不在 daemon 内再增加所有权锁；不遗留延迟输入或后台 GUI 写任务。
- 保持原生 Cua 协议兼容。远端 coding-agent/命令通道和 Cua Spaces App 的既有兼容例外不在新增业务操作时顺带扩大、改造，也不作为绕过 GUI 锁的通道。

## 3. 前置条件与结果

- daemon 缺少前置条件就返回错误，说明当前问题及需要满足的条件；由客户端脚本或 Agent 决定下一步。固定补足步骤可写进 Skill 脚本，需要判断的步骤交给 Agent/Cua。
- 沿用结构化错误：`code`、`error`、`execution`，必要时加 `precondition`、`next_action`。`next_action` 是建议，服务端不自动执行；MCP 必须将详情传给 Agent。
- 区分 `not_started`、`partial`、`unknown` 与已完成的本地动作。部分执行或结果未知时先观察，不盲目重复发送、点击或提交。发送等不可随意重复的操作沿用 request_id/收据机制。
- 目标引用绑定调用者、应用/窗口身份和有效期；写入前重新核对当前目标及已有草稿。缺失、过期、多义或不支持的界面应明确失败，不猜测目标。
- 报告可观察的事实：回车提交不等于网页加载完成，新文档不等于文章可读，发送动作或本地数据库记录不等于对方收到/已读。等待和重试必须有界，不能为“验证成功”重复产生业务副作用。

## 4. 已有模式与后续示例

| 任务 | daemon / 数据层 | 客户端 Skill |
| --- | --- | --- |
| 打开公众号 URL（已实现） | `browser_state`；`navigate(page="web_search")`；`browser_open_url(window_ref,url)` | `open-url` 脚本：获锁 → 查询 → 缺窗口时进入搜一搜 → 提交 URL → 只读观察 → 释放 |
| 公众号文章点赞/爱心（已实现） | `browser_article_state`；`browser_article_react(article_ref,expected_url,reaction,request_id)`，只确保点亮当前文章的一个反应 | `react-article` 脚本：获锁 → 核对文章 → 逐项调用并只读验证 → 释放；已关注公众号查找/有界选文/分段浏览由同一客户端脚本组合原子接口和原生 Cua 滚动，详见[实施说明](WOC-WeChat-公众号文章互动.md) |
| 给联系人/群发文本（已实现） | 数据查询；页面观察/导航/搜索/打开项；核对草稿的 fill/send | 解析准确目标；当前可见就打开，否则搜索；填入、核对、发送、检查收据；不逐屏翻列表 |
| 导出本地尚未下载的视频（分层示例，未实现完整 UI 编排） | wx-cli/daemon 返回本地文件缺失，不自动点击下载 | Agent 在锁内定位消息并触发下载，或调用以后已有的原子操作；准备完成后再调用导出。固定流程成熟后才放入 Skill 脚本 |

应用接口保留应用命名空间。实例的桌面模式与应用能力是不同维度：完整桌面也可能运行微信；不能仅凭容器名称或调用者声明的 type 决定能否执行。新增 QQ/独立浏览器时按对应适配器实现，避免把所有应用逻辑塞进微信模块，也无需提前实现尚未需要的框架。

## 5. 新增操作的实施要求

1. 先按第 1 节说明操作归属、读/写性质、输入目标、前置条件、成功证据和失败语义，再改代码；说明可写在任务实施记录或提交说明中，不要求额外审批流程。
2. GUI 接口在 [统一契约](../../panel/server/src/business/ui-contract.mjs) 定义 HTTP/MCP 参数及读写分类；数据接口参照 [数据契约](../../panel/server/src/business/contract.mjs)。同时更新 daemon 校验/分发，保持契约一致。
3. 确定性编排放入 [Skill scripts](../../integrations/skills/woc-wechat/scripts/)，在 [SKILL.md](../../integrations/skills/woc-wechat/SKILL.md) 写明调用入口、参数和异常处理边界。不要只在提示词中逐条描述可脚本化的固定步骤。
4. 按变更验证关键分支：无锁读、无锁写拒绝、持锁执行、前置条件缺失、失效目标、失败后释放/不盲目重试；新增入口用真实客户端 Skill/MCP 贯通验证。只报告实际验证结果，真实发送沿用用户对目标和内容的授权。
5. 新增 daemon 文件同步安装器、初始化脚本、镜像清单；记录兼容条件、部署范围和回退方法。原始聊天、密钥、带会话参数的 URL 和截图保留私有，不进入公共文档。

本文件维护分层原则；[系统架构](WOC-Cua-系统架构.md) 维护拓扑及代码位置；调研/验收文档维护具体版本的证据。后续用户修改架构约定时同步更新这里，避免多份规范互相冲突。
