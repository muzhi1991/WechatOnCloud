# 消息访问与人机协作监控方案

2026-10-28；研究基线：本仓库 `8530306`。**本文是待确认设计，不代表数据库读取、消息监听或自动回复已经实现或获得运行授权。** 本次只阅读源码和公开文档，没有安装或运行 wxcli，没有读取微信进程内存、数据库或密钥。用户举例的“三次尝试”是希望采用的授权机制，目前可执行预算为零。

建议先完成 P5 和过夜观察，再实现只观察、可回补、不会发消息的 UI 监控试点；数据库作为独立读取适配器研究。日常任务、面板按钮与后续 AI 对话共用一个受管任务接口，不把发送权限交给模型自由决定。

## 1. 证据与边界

| 结论 | 状态与来源 |
| --- | --- |
| WOC 将容器图形桌面通过 KasmVNC 显示在网页中 | 已证实。它不是把微信聊天转换成可查询的网页 DOM。当前 [Desktop.tsx](../../panel/web/src/pages/Desktop.tsx) 使用 VNC iframe / websockify；KasmVNC 官方将其定义为桌面和应用的浏览器流式访问。[官方说明](https://docs.kasmvnc.com/docs/latest/) |
| 微信部分内容可以从辅助功能树读取 | P5 实测覆盖搜索框、文件传输助手和另一个账号发来的单条测试消息节点；没有证明所有聊天类型、历史消息、附件和隐藏窗口都完整可见。[P5 验收](Cua-P5验收记录.md) |
| 可在人工操作时继续无输入截图/读树 | 当前网关已将 Screenshot/GetTree 等划为 read，viewToken 可以调用；这是技术入口，不表示已建成监控服务。截图不会切换聊天，但观察范围受遮挡、窗口状态、辅助功能实现影响。[协议分类](../../panel/server/src/control/protocol.ts)、[网关](../../panel/server/src/control/gateway.ts) |
| 人工可抢占，Agent 不能抢人工 | 已实现短期租约、epoch 失效、输入排空、维护锁；新监控必须接入同一机制。[leases.ts](../../panel/server/src/control/leases.ts) |
| RPC 返回成功意味着微信操作成功 | 不成立。当前 journal 的 done 记录的是 RPC/任务生命周期；业务必须另核验画面和语义。[P5 验收](Cua-P5验收记录.md)、[journal.ts](../../panel/server/src/lifecycle/journal.ts) |
| GUI 一定比读库安全，或限制三次就不会封号 | 无证据支持这样的概率/保证。减少探测次数能控制执行范围，不能换算成账号风控概率。 |

因此可以“像人一样看界面”，但不能仅监听浏览器 DOM 就得到完整消息流。画面变化也可能来自鼠标、动画、时钟、遮挡或用户切换聊天，不等于新消息。微信其他设备的操作不经过本面板租约，同样会影响会话状态。

## 2. wxcli 的项目范围与原理

前次工作区研究明确提到的是 [anyshu/wxcli](https://github.com/anyshu/wxcli)，固定快照 `08af894594b4afd468e23e17dbd783f15403f13b`；本次网页显示它 fork 自 `hydewww/wxcli`。此前提到的 [jackwener/wx-cli](https://github.com/jackwener/wx-cli) 本次访问仍返回 HTTP 451，无法声称核验了其最新版本。本文结论限定为可读 fork 的上述快照，不混用几个仓库或假定同名项目实现一致。[前次研究](../../../research/wechatoncloud-principles-2026-10-28.md)

该快照的读取链路如下：

1. Linux 扫描器查找名称为 wechat/weixin 的进程，读取 `/proc/<pid>/maps` 与 `/proc/<pid>/mem`，扫描可读写内存区域中的候选密钥，并与数据库 salt 匹配。它是进程内存读取路线；当前代码取首个匹配进程，没有为我们的实例提供明确 PID 绑定。[scanner/linux.rs](https://github.com/anyshu/wxcli/blob/08af894594b4afd468e23e17dbd783f15403f13b/src/scanner/linux.rs)
2. 解密器以固定 4096 字节页布局执行 AES-256-CBC 解密，输出另一个 SQLite 文件；这不是微信官方查询 API。该函数未做页 HMAC 验证，不能把“解密函数没报错”当成数据完整性证明。[crypto/mod.rs](https://github.com/anyshu/wxcli/blob/08af894594b4afd468e23e17dbd783f15403f13b/src/crypto/mod.rs)
3. daemon 加载密钥并维护联系人、会话等查询上下文；启动预热会访问联系人、session 和 sns 数据。直接启动完整 daemon 超出了“只验证某个测试会话”的最小范围，故不建议照搬启动。[daemon/mod.rs](https://github.com/anyshu/wxcli/blob/08af894594b4afd468e23e17dbd783f15403f13b/src/daemon/mod.rs)
4. 缓存比较数据库与 WAL 的修改时间，决定复用、应用 WAL 或重新全量解密；README 提供 sessions/history/new-messages 等读取命令。研究这些实现可以指导适配器，但这些命令尚未在我们的微信版本上实测。[cache.rs](https://github.com/anyshu/wxcli/blob/08af894594b4afd468e23e17dbd783f15403f13b/src/daemon/cache.rs)、[README](https://github.com/anyshu/wxcli/blob/08af894594b4afd468e23e17dbd783f15403f13b/README.md)

**一致性审查发现：** 固定快照的 `apply_wal` 遍历完整帧，检查页号范围和 salt 后写入解密文件，但没有使用 `commit_pgcnt` 限定最后提交事务，也未验证 WAL 累积 checksum。SQLite 规范区分有效帧、提交边界和读事务的 end mark。推断：并发写入或 WAL 轮换时，此实现不足以保证读取的是一个已提交、一致的消息快照；这不是对当前账号数据已经损坏的结论。[apply_wal 源码](https://github.com/anyshu/wxcli/blob/08af894594b4afd468e23e17dbd783f15403f13b/src/crypto/wal.rs)、[SQLite WAL 格式](https://www.sqlite.org/fileformat2.html#wal_file_format)、[SQLite 读事务说明](https://sqlite.org/wal.html#concurrency)

我们若自行实现，需要先用合成数据验证页完整性、提交边界、WAL reset/checkpoint、截断、复制期间文件变化、多分片及失败恢复。仅比较 mtime 或对输出执行 integrity_check，不能证明它代表目标时刻的一致快照。不要把一个可查询的文件直接接成自动回复的数据源。

未知项：Linux 微信 4.1.13.26 的密钥表示、实际进程权限、数据目录/schema、消息 ID 稳定性、附件编码、轮换行为与本快照的兼容性；账号风控影响。当前均未运行验证。

## 3. 数据库限次授权与实验计划（尚未执行）

授权对象应是可查看的执行清单，不能是“你可以试试”的无限循环。建议 `ProbeGrant` 包含：实例 ID + 容器 ID/generation + 账号指纹、固定代码提交/脚本 hash、目标 PID/DB 范围、允许动作、最大尝试数、单次时间/读取字节上限、有效期、输出允许字段、保存期限、失败停止条件。账号或容器 generation 变化使授权失效。

建议把**一次尝试**定义为一次已经扣减预算的受限探测运行：最多一次目标进程内存扫描，以及授权清单指定的有限文件快照采集；不得在一次运行里隐藏多次扫描、自动重启再扫或切换其他账号。已取得副本后的离线解析和合成测试不消耗新的实时探测次数，但不得扩大获准读取内容。读到部分数据、超时或进程崩溃都算一次；不把“没成功”解释为免费重试。

执行器必须在任何实时读取前事务性、持久化地扣减次数；串行运行；同一请求 ID 重放返回既有记录，不重复执行；崩溃后预算不返还。下一次失败重试前展示本次结果、剩余预算及变更点；如果用户选择逐次确认模式，则每次都要确认。若只批准总预算且脚本/范围不变，仍不得超出累计预算。

| 阶段 | 允许工作与退出条件 |
| --- | --- |
| D0 纯研究 | 固定源码、列出读取面；合成 DB/WAL 测试；定义探测清单和输出。当前所在阶段，不触碰真实库。 |
| D1 经明确授权的单次探测 | 仅指定新实例；显式绑定 PID，禁止扫描宿主机其他进程；只读已批准路径；最小范围验证密钥候选和副本，禁止原库写入。超时/权限不足/异常立即停止。 |
| D2 离线验证 | 对已批准副本检查完整性、schema 和指定测试消息；先只输出“匹配/不匹配、条数、版本”，内容展示须在授权范围内。失败不得自动重新抓实时数据。 |
| D3 只读适配器试点 | 另行确认是否持续采集、会话范围、频率及保留期；不能由“三次探测”推导成无限监听授权。先影子验证，再考虑作为对账来源。 |

任何要求新增容器权限、放宽 ptrace/Yama、挂宿主机 PID、暂停/重启微信、注入/修改进程、扩展到更多库或账号、上传数据到外部服务的动作均不包含在普通读库预算内；需要展示具体变更和理由，再由用户二次确认。不能用加 `--privileged` 自动修复权限错误。

密钥、原始内存及明文缓存不进入日志、Git、模型上下文或常规备份。默认不保存原始内存；副本放私有目录并按用户确认期限清理。模型只看到任务所需、用户允许的数据。原库只读不代表没有隐私或维护风险。

## 4. UI 监控：先观察，再按需接管

推荐双层结构：轻量 Observer 常驻读截图/树和控制状态，Reconciler/Executor 只有取得租约才导航或输入。

- Observer 首版采用受管 Screenshot/GetTree 的低频采样（试点建议 10–30 秒、上限可配置），只监控用户勾选会话和微信窗口。先做区域 hash/树差异去抖，确有变化再解析；图片变化只是线索。该频率是资源折中，不是风控安全阈值。
- 优先使用当前已证实的辅助功能语义，截图交叉核验，必要时 OCR/模型辅助；低置信度保留待核验，不生成可自动回复的确定事件。
- 初期不解码 KasmVNC 私有帧协议，也不靠每个浏览器标签页运行监听。独立服务在网页关闭后仍可工作；页面只订阅状态。未来可评估事件推送优化，但不改变消息完整性边界。
- 被动观察不改变焦点、聊天选中状态或滚动位置。需要展开未读、打开聊天、向上滚动读历史时，已经是输入操作，必须申请与人工共用的租约。
- 对看不见的消息声明 coverage gap：窗口隐藏、其他应用在前、列表截断、UI 虚拟化、采样间隙突发、消息撤回都可能造成遗漏。UI 路线不承诺全量、无丢失、实时归档。

人工持有时推荐保持可选的**被动观察**，但默认只保存可见范围的结构化线索，不记录输入框中的草稿，不全屏录制其他应用。设置“人工操作时暂停观察”隐私开关；暂停也记录 gap 起止。两种模式都停止自动输入、回复和主动翻页。人工读过消息使未读红点消失，不得据此丢弃之前待处理事件或认为此前消息已经被回复。

## 5. 协作状态机与恢复对齐

不要把监控状态塞进现有控制状态枚举。现有 `idle/human/agent/handover/faulted/maintenance` 继续是唯一输入仲裁；新增独立监控状态，并订阅租约/实例事件。这样不会产生两个互不认识的锁。

| 监控状态 | 可以做什么 | 主要转移 |
| --- | --- | --- |
| OFF | 仅显示未启用 | 用户启用 → BASELINE |
| BASELINE | 无发送；建立当前账号、会话、可见消息锚点，旧消息不触发回复 | 完成 → OBSERVING；人工持有 → HUMAN |
| OBSERVING | 被动采样、去重、生成候选事件 | 需要导航且桌面空闲 → RECONCILING；人工接管 → HUMAN |
| HUMAN | 按设置被动观察或暂停；冻结旧计划，不操作桌面 | 人工释放 → RECONCILING |
| RECONCILING | 取得短租约后重新识别账号/窗口/会话，按批准范围回看重叠历史 | 完整性足够 → OBSERVING/待确认任务；无法对齐 → NEEDS_REVIEW |
| EXECUTING | 执行已授权任务；每个输入检查当前 epoch/generation 与前置条件 | 完成并核验 → OBSERVING；人工抢占 → HUMAN；结果不明 → NEEDS_REVIEW |
| NEEDS_REVIEW | 保留证据和 gap，禁发；可继续被动观察 | 用户处理或明确重新建立基线 → RECONCILING |
| SUSPENDED | 维护、离线、重启、登出；不解析为新消息 | 恢复就绪 → BASELINE/RECONCILING，旧计划不复活 |

人工接管的瞬间：同步使旧 epoch 的计划无效；撤销待执行发送；对已发出的 RPC 等待排空。已经实际点击发送的消息不能撤回为“没发送”，结果必须归为待核验。模型即使稍后返回旧推理结果，也因 epoch/基线版本不符而被丢弃。

交回后的对齐顺序：

1. 等待维护和交接结束，取得新租约；读取最新截图/树，识别账号、微信窗口和当前会话，不能沿用旧坐标/元素 token。
2. 检查当前草稿。非本任务创建的内容不得清空/覆盖；记录冲突并等待用户处理。不得为了“恢复监控布局”打断人工尚未完成的编辑。
3. 对获准会话重扫最近一段历史，与交接前最后数条已确认消息重叠匹配；未读数仅作提示。后台必须保存锚点和 gap，不能仅保存最后一次截图。
4. 发现人工或手机端新增的自己消息时，取消或重新生成此前待发回复，避免重复回答。UI 中的“自己发出”一般不能确定究竟来自人工、手机还是 Agent；只与我们已知发送记录匹配，其他视为外部活动。
5. 有匹配锚点且区间可解释时更新水位；找不到锚点、重复文本无法区分、消息超出获准回溯范围时保持 gap，转人工复核，不能宣布已经全部同步。
6. 重新评估策略后才允许产生新的发送任务；人工释放并不等于批准执行被中断的旧计划。

同一实例一次只运行一个主动 UI 任务；多实例可独立排队。Reconciler 使用有限时间片并释放控制，避免常驻监听长期占有桌面。打开聊天可能改变微信已读状态，这是主动监控的产品行为，启用前必须在面板讲明并由用户选择。

## 6. 消息事件、幂等与自动回复

建议统一 `MessageObservation`：`instanceId/accountEpoch/source/chatRef/observedAt/sourceTime/contentType/direction/evidenceRef/confidence/coverage/leaseEpoch`；账号变化开启新 accountEpoch。UI 没有稳定 message ID 时，用会话、方向、归一化内容、时间提示、相邻消息序列做候选匹配；相同内容重复发送不能简单 hash 去重，歧义事件进入复核。DB ID 只有验证唯一性和生命周期后才能作为适配器游标。

分别持久化观察记录、对齐水位、回复计划与发送意图；正文与证据使用私有存储及保留策略，控制 journal 只引用不含内容的 ID。提交游标前先持久化事件，崩溃后可重放去重；UI coverage 表示“验证过的可见区间”，不能冒充微信全量消息 offset。

发送意图状态：`proposed → approved → dispatching → verified | uncertain | cancelled`。在调用输入前写入 dispatching；发送前重新检查目标会话、内容、草稿、账号、epoch、触发消息仍有效；触发消息已获回复或发生人工活动则取消旧计划。点击发送后观察气泡/错误标志与编辑区，并区分“UI 出现气泡”和“对端已收取”。

本地唯一 intent ID 能阻止我们的同一任务重复调度，不能让 GUI 发送具备端到端 exactly-once。发送后断网、超时、进程重启等使结果不确定时，**不自动重发**；先对账或交用户处理。租约只解决本桌面输入冲突，解决不了同时在手机发送造成的远端竞争，所以第一版自动回复应为生成建议、人工确认后发送。

自动发送属于以后单独批准的模式：限定实例/会话、时段、内容类别、速率与每轮次数，有停止开关；默认排除群聊、未知身份和历史回补消息。模型输出经策略校验后才交执行器。当前单次“CUA 微信集成测试”的授权不延伸到自动回复。

## 7. 日常操作如何封装

| 类型 | 适合实现形式 | 边界 |
| --- | --- | --- |
| 租约申请/释放、状态检查、截图/读树、排队、日志、预算 | 确定性脚本/服务 API | 一处实现，被 CLI/面板/AI 共同调用 |
| 已验证版本的找会话、确认标题、读可见消息、输入/取消本任务草稿、单次发送 | 参数化步骤与前后置断言 | 界面不符合预期立即返回需判断；不写固定坐标盲点脚本 |
| 名称歧义、异常弹窗、附件/表情理解、跨聊天归纳、复杂导航 | AI workflow | 消息文本是数据，不能作为越权操作指令；只输出受约束计划 |
| “读取指定聊天”“提出回复”“经批准发送” | Skill 描述策略 + 调用上述 API | Skill 不保存密钥，也不独立实现另一套锁/授权 |
| 面板按钮/AI 对话 | 同一任务服务的客户端 | 展示目标、操作内容、范围、当前控制者和结果证据；不直接调用原始 Docker/Cua 写接口 |

建议领域接口先定为 `observeChat`、`reconcileChat`、`prepareReply`、`sendApproved`、`cancelOwnedDraft`，适配器实现 `ui` 或未来 `db-read`。读取返回 coverage/confidence，调用方必须处理“不完整”；发送统一走 UI 与租约。DB 适配器不会自动获得发送或内存探测权限。

UI 工作流与 DB 工作流可以共用上层任务语义，但不伪装成等价：DB 若可用可提供更稳定读取，UI 可提供发送及现场复核；两路证据不一致时保留来源、冻结自动回复，不“选一个看起来正确的”。

## 8. 分阶段实施与验收

| 阶段 | 建议工作 | 验收与批准边界 |
| --- | --- | --- |
| P5 收尾 | 草稿取消、登录后人工接管、接收测试、过夜运行观察 | 继续原计划；过夜只记录运行健康，不默认采集聊天/截图；接收须有实际手机回传证据 |
| M0 状态机/接口 | 用合成事件实现监控状态、watermark、发送意图、授权预算和恢复测试 | 纯测试数据；无真实监控、无实时 DB |
| M1 UI 影子观察 | 用户选一个测试会话；被动观察并报告候选与 gap | 确认范围/保留期后启动；零自动发送；比较人工操作期间及交回后的结果 |
| M2 主动对齐 | 授权有限导航/历史回看、短租约、草稿保护 | 用户理解已读变化；重复内容、遮挡、突发、断线、人工期间切换聊天均有可解释结果 |
| M3 辅助回复与日常 Skill | 建议回复、人工确认、共享任务 API/面板按钮 | 一次批准绑定一次发送意图；超时不重发；回补消息默认不触发 |
| D1–D3 独立 DB 试验 | 按上文单独授权推进 | 不阻塞 UI 路线；试探预算用尽即停止 |
| M4 自动回复 | 仅在可观测性/冲突策略验证后考虑 | 新的明确策略授权；不能沿用 P5 授权 |

重要测试：人工持有期间不产生写 RPC；旧 epoch 推理返回不发送；人/手机已回复使待发计划失效；重复消息不被错误合并；无法回补时显式 gap；发送已点击但确认丢失不重发；重启不恢复过期计划；账号切换清除旧账号游标；源数据库修改不自动启动新的密钥扫描；并发探测请求不突破预算；预算扣减后崩溃仍计次。

待用户确认的产品决定（方案阶段提出，暂不执行）：监控会话范围、人工时继续被动观察还是暂停、主动打开聊天/改变已读是否接受、回补上限与保留期、首版是否坚持逐条人工确认发送。数据库具体目标与预算要在 D0 清单完成后另批；“允许监控”也不等于“允许将聊天传到模型 API”。后续 AI 面板需明确模型供应商、可出站数据和工具权限。

完整桌面入口及 AI 对话面板是独立需求，应各自方案确认、各自提交；它们使用同一租约与任务 API，不应为方便而绕过现有 WOC 的人工接管和维护锁。
