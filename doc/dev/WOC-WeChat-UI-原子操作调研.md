# 微信 UI 原子操作：网页输入机制与实测

这是接口实现之前的调研记录，保留当时的事实与候选设计。后续已实现并部署，当前接口及测试结果以 [首版验收](WOC-WeChat-UI-验收.md) 为准。

日期：2026-10-30。范围：源代码调研、原生 Cua 受管通道上的两次授权文本发送、后续接口拆分建议。尚未新增生产 daemon GUI 接口、业务 MCP 工具或客户端微信 Skill；不能把本次原生 Cua 测试当成新接口验收。

## 1. 用户确认的职责

调用单向：客户端 Agent / Skill 脚本 → WOC 网关 → 容器 daemon → 本地执行。

- 客户端显式申请和释放 GUI 写锁。网关、daemon 不自动申请锁，也不补做前置 GUI 操作。
- daemon 以应用专属原子操作为主；高频稳定小流程才考虑适度合并。复杂流程放在客户端。
- 常用确定流程写成 Skill 附带脚本，直接调用多个认证 HTTP API 并按结果分支；SKILL.md 指定脚本入口。需要观察和决策的部分才由 Agent 处理。
- WOC 能力属于应用语义，例如微信填写草稿、发送当前草稿；原生 Cua 继续提供通用 computer-use。
- 首版只适配微信，但保留 provider / capability 结构，未来可加入 QQ、浏览器；显示模式与应用类型分离。

## 2. 网页底部“发送”真实实现

入口为 [Desktop.tsx 的 sendImeText](../../panel/web/src/pages/Desktop.tsx)。流程是：

```text
网页输入栏的文本
  → POST /api/instances/:id/type
  → 后端认证 / 实例权限 / humanWrite
  → typeInInstance：容器 xclip 设置剪贴板，xdotool 发 Ctrl+V
  → 如果网页“自动回车”开关打开，再调用 key 接口发 Return
```

源码位置：

- [前端 Desktop.tsx](../../panel/web/src/pages/Desktop.tsx)：sendImeText、autoEnter、输入提示。
- [后端 index.ts](../../panel/server/src/index.ts)：`/api/instances/:id/type`、按键路由；type 限制非空且不超过 500 个 JS 字符单位。
- [docker.ts](../../panel/server/src/docker.ts)：typeInInstance、X_PRELUDE、xdoKey、剪贴板处理。
- [control/runtime.ts](../../panel/server/src/control/runtime.ts)：humanWrite 包装同一 ControlLeases.write。
- [docker/control/http-input](../../docker/control/http-input)：flock 和 timeout 约束在途本地输入，避免交接后残留写动作。

它是一套通用远程输入桥，并没有调用微信内部发送接口。不会查找联系人，不核对聊天标题，也不定位微信编辑框；依赖用户先把容器内焦点放在正确输入框。前端“发送”实际上由两次调用组成：粘贴，再可选回车。HTTP 成功只表示底层命令返回，不代表消息发送成功或对方收到。

值得复用的实现经验：

1. 剪贴板粘贴规避 VNC 中文输入法 / keysym 限制，不逐字模拟中文输入。
2. 文本通过编码/文件传输，避免 shell 插值；新实现应优先 stdin 和固定 argv，不开放任意 shell。
3. xdotool 先释放修饰键，避免残留 Ctrl/Shift 影响后续输入；不能照搬 `--clearmodifiers` 的恢复语义。
4. 受管实例取消延迟剪贴板恢复，避免锁交接后旧任务再次改剪贴板；新实现不能引入后台延迟动作。
5. 当前剪贴板备份仅支持一种常见格式、有大小边界；粘贴会改变剪贴板，不可承诺无副作用。

## 3. 比 Cua 更稳定吗

对“网页输入中文”这个具体问题，剪贴板桥有明确作用；但不能据此说它比 Cua 更可靠。两者最终都影响同一 GUI，使用 xclip/xdotool 也仍然依赖焦点、应用状态和正确目标。

如果只复制网页逻辑，自动化时很可能向错误输入框粘贴或在错误聊天按回车。更可靠的组合是：微信专属结构定位和目标检查 + 已验证的剪贴板输入 + 发送前草稿校验 + 结果观察。

可以将成熟的低层输入方法提取到 daemon；现有网页接口保留原人工行为，首版不为了复用而整体重构原 WOC。Cua 可以作为 GUI 执行后端或异常时的通用工具，不能把“业务语义封装”和“底层输入机制”混为一谈。

本轮验证的是原生 Cua 的剪贴板写入、粘贴与结构定位点击。没有直接调用人工网页 Cookie API，也没有把未经网关检查的 SSH/进程命令作为 GUI 写入路径，因此没有宣称独立 daemon 的 xclip/xdotool 实现已经验证。

## 4. 真实发送结果

仅使用现有微信实例 `77bafd5161`（Cua 名称 `woc-p3-77bafd5161`，容器 `woc-wx-77bafd5161`，受管入口 13341）。所有 GUI 写入通过原生 Cua MCP → WOC 网关，显式使用 WOC MCP 获取/释放锁。

开始时网页 admin 持锁，未执行任何 GUI 写入。用户明确交回后才申请锁。联系人查询对“李牧之”返回一个匹配项，当前聊天标题与该联系人一致；没有把 UI 显示名当成从 UI 获得的数据库 chat ID。

| 测试 | 动作与结果 |
| --- | --- |
| 当前聊天发送 | 在“李牧之”空输入框填入“WOC 文本发送验证”；结构读取与截图核对草稿后点击发送按钮；消息列表出现正文，输入框清空，发送按钮禁用；数据库对应聊天返回新文本记录 |
| 切换聊天后发送 | 用户追加授权文件传输助手；从当前结构定位该会话并点击；重新读取结构确认标题与空草稿；填入“WOC 切换聊天发送验证”，重新定位发送按钮并点击；界面出现正文、草稿清空；首次数据库查询仍为旧记录，稍后再次查询读到新记录 |
| 控制交接 | 两轮均显式获取同一机器写锁，操作结束释放；未改变原生 Cua 代码或网关策略 |

发送按钮由结构返回的快照 token 定位，原生 Cua 实际派发前台指针点击；本轮未证明微信支持 AT-SPI 原生 Invoke/Press 直接发送。结构中该按钮主要显示 SetFocus，不能将“能读到按钮”推断成“可无焦点直接调用发送”。

两次测试只说明当前 Linux 微信版本和两个已存在聊天的路径可行，不代表广泛可靠性统计。还没覆盖陌生聊天搜索、同名联系人、群聊、离屏会话、输入法异常或人接管发生在动作中途。

两条消息最终均取得界面与本地数据库记录两种证据；不宣称接收方已读。文件助手第一次查询落后说明 checkpoint_only 数据可以滞后，这次不是精确 WAL 延迟测量，不能据此承诺同步时间上限。第二轮结束桌面停留在文件传输助手，锁为 free。

私有 MCP 结果与截图在忽略目录 `artifacts/wechat-ui-send-research/`，不提交消息历史、截图、账号标识和凭证。本记录只保留用户指定的测试对象和测试文字。

## 5. 结构定位的实际约束

- “李牧之”编辑框与文件传输助手编辑框的节点序号不同；发送按钮序号也不同，不能固定数字或跨快照使用 token。
- 草稿为空时发送按钮禁用，填入后启用。发送前可读取编辑框 value 并与 expected_text 精确比较。
- 发送后编辑框名称可能附带“按住鼠标 语音输入文字”等提示，不能只凭编辑框完整 Name 判断当前聊天。
- 当前聊天应由标题、会话选中情况、编辑区上下文共同确定；UI 尚未提供可靠内部 chat ID，同名或无法核实身份时应返回前置条件，由客户端处理。
- 既有 Qt5 AT-SPI 调研发现 GetAll 可导致应用崩溃；后续自写适配必须沿用逐项 Properties.Get、明确超时和读取预算，不使用 GetAll 或自动属性缓存。

## 6. 建议首版应用接口

以下名字是候选契约，不代表已经实现。

| 操作 | 写锁 | 范围与前置条件 |
| --- | --- | --- |
| `wechat.ui_state` | 不需要 | 当前窗口、聊天显示信息、可见会话候选、草稿、发送是否可用、身份核实程度 |
| `wechat.select_visible_chat` | 需要 | 只选择当前已观察到且唯一匹配的可见会话；不可见或有歧义直接报错，不自动搜索滚动 |
| `wechat.fill_text` | 需要 | 核对当前聊天、编辑区与预期草稿状态后粘贴；默认要求原草稿为空，不覆盖用户草稿；不发送 |
| `wechat.send_draft` | 需要 | 核对当前聊天与 expected_text 后点击当前发送按钮；不自动填字、不切换聊天；带 request_id，未知结果不重发 |

WOC MCP 可对应 `woc_wechat_ui_state`、`woc_wechat_select_visible_chat`、`woc_wechat_fill_text`、`woc_wechat_send_draft`。HTTP 继续走微信应用命名空间，不为了新增应用复制认证/锁实现。

daemon 按 provider 分离微信定位逻辑和共享本地输入工具。网关检查应用能力而不只相信调用者的 type；完整桌面也可能运行微信。未安装、未登录、多个候选进程或不支持的版本应明确返回，而不是执行通用输入碰碰运气。

## 7. 客户端 Skill 脚本的固定流程

建议 `woc-wechat/scripts/send-text` 负责：解析目标 → 获锁 → ui_state → 必要时 select_visible_chat → fill_text → 读取并核对草稿 → send_draft → 释放锁 → 查询发送记录。

脚本直接通过现有认证 HTTP API 调用，不要求每个确定步骤都回到模型。前置条件不满足、锁被抢占或结果未知时向 Agent 返回结构化上下文，不能自动持续抢锁或重放发送。finally 只释放本次获得的 lock_id，不能释放另一个流程的新锁。

SKILL.md 指定何时运行脚本、如何提供准确聊天标识、哪些错误需要重新观察；复杂搜索、滚动到旧媒体等由 Agent 使用原 cua-spaces Skill。下载媒体仍是“读取返回未就绪 → 客户端准备 UI → 再读”，不会被隐藏进 daemon。

共享客户端身份的脚本需要串行，第一版不引入服务端工作流引擎。涉及写副作用的 HTTP 错误须保留 execution / precondition / next_action；当前 WOC MCP 错误适配会压缩成字符串，接入上述接口时必须一起改为保留结构化结果。
